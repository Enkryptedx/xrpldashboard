## Root cause (why 60 days of retry-and-park)

Two overlapping failure modes, each of which would independently mask the other:

### 1. Drive was never initialized
Reported `Content: None`, `Partition Map: Not Supported`. No partition table, no filesystem. Any `diskutil` operation targeting a volume/partition inside it would fail because there was nothing there to target. Every prior "let me try formatting it" attempt via GUI or terminal was hitting a bare-metal SSD with zero prior state.

### 2. Terminal.app lacked Full Disk Access grant
macOS 13+ requires apps to hold Full Disk Access (or the narrower "Removable Volumes" grant) before they can touch external volumes' filesystem paths. **Without FDA, filesystem access hangs silently instead of erroring.** This is the critical failure mode:

- `diskutil eraseDisk` → hangs indefinitely (no error, no timeout, no dialog)
- `ls /Volumes/DockVault` → hangs indefinitely
- `echo > /Volumes/DockVault/file` → hangs indefinitely
- `sudo mdutil -i off` → hangs indefinitely (sudo's own auth path indirectly touches TCC state)

Because every attempted diagnostic ALSO hung the same way, every prior triage looked like "the dock is broken" or "the enclosure is dead" or "the drive is bad." Finder worked fine (different code path, holds its own TCC grants), which added to the mystery — GUI could see the drive, terminal couldn't touch it.

### Contributing factors layered on top

- **macOS "The disk you attached was not readable" auto-mount dialog.** Blocks `diskutil` operations until dismissed (Ignore / Initialize / Eject). If unseen, diskutil hangs waiting.
- **Disk Utility.app running in background races with terminal `diskutil` for disk locks.** Even if terminal had FDA, an open Disk Utility.app window on the same disk causes indefinite hangs.
- **Zombie `diskutil` processes from prior interrupted attempts** hold disk locks until killed (`ps -ef | grep diskutil`).

### Why APFS Encrypted

- Full-disk encryption is the standing rule for local storage — same class as FileVault-on-Mac.
- Encryption protects the physical-theft threat model: drive lives at Charlie's home desk, threat is theft-when-Mac-is-off. Encryption keeps data inaccessible to a thief who walks off with the dock.
- Native APFS integration: encryption is transparent to applications, survives reboots, supports keychain-remembered unlock for scripted access.

## Wounds surfaced during ceremony

### #1 — Terminal.app FDA gap (fixed for Terminal, meta-lesson pending)

Terminal.app was missing Full Disk Access when the ceremony started. Enabling it fixed the entire class of hangs immediately.

**Meta-lesson filed:** every macOS process that touches external volumes needs its own FDA grant, verified in its own runtime context. Python interpreters running under `launchd` have their OWN FDA state separate from Terminal's. Any future automation that writes to DockVault must verify FDA in the actual runtime context — a Terminal-level test does NOT prove that a launchd-spawned Python process can access the volume.

This is the same class of failure as the TCC LAN grant lesson from 2026-08-16 sovereignty-exile fix: launchd context ≠ Terminal context ≠ Finder context for macOS permission grants. Every automation host must be tested in the context that will actually run it.

### #2 — Cloudflare WARP still listed in Full Disk Access

Memory record says WARP was removed 2026-08-16 during sovereignty-exile fix (`systemextensionsctl list = 0 extensions confirmed clean`). The FDA list still shows a Cloudflare WARP entry. Two possibilities:
- **(a)** Stale dead-app pointer — app deleted, FDA registration lingered
- **(b)** App still installed, only network extension removed (partial uninstall)

Not a fire. Low-priority census follow-up: `ls /Applications/ | grep -i warp && ls /Library/Application\ Support/Cloudflare/` and reconcile.
