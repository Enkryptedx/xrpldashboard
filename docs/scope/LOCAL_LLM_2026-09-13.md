## 3. WHY THE EARLIER TEST WAS BAD

From `memory/feedback_llama_8b_insufficient.md` (dated 2026-05-14):

- **Model:** `llama3.1:latest` (8B parameters, Q4 quantization, ~4.9 GB weights)
- **Ollama version at test time:** 0.23.2
- **Prompts:** two real-world entity attribution tasks — "GTreasury legitimacy check" + "OpenEden vs Midas TBILL: who issues on which chain?"
- **Tools available:** **NONE.** Pure prompt-in / text-out. No web search, no MCP, no RAG.
- **Failure modes observed:**
  - Missed GTreasury as a real Chicago treasury-mgmt SaaS firm (blind spot)
  - Got 1 of 4 attribution facts correct on OpenEden vs Midas TBILL
  - **Self-reported false training cutoffs** ("2022-02", "2023-02"; actual cutoff ≈ July 2024) — model cannot self-report reliably

**Root cause: wrong task shape for the model, not the model quality.** LLMs at the 8B scale have limited world-knowledge recall and no way to update it. Asking an 8B to recall "did OpenEden ship on XRPL" is exactly the wrong question. The RIGHT question shape for a small local LLM is *synthesis given evidence*: "here is the /check.json signed response for issuer X, tier=verified, source=curator+two-way-toml, observed_at=..., write me a one-sentence answer citing the source." Under that shape (RAG + tool grounding), 8B-class models score much higher.

**Rule for the next attempt:** the eval questions ALL come with tool-grounded evidence available. The score is not "does the raw model know" but "does the tool-using assistant produce correct, cited answers."

| `issuer_facts` PG rows (10,663 rows × ~150 chars) | ~1.6 MB serialized | daily |

**Corpus total: ~8 MB text.** That's tiny — fits comfortably in memory. At ~500 chars/chunk, ~16,000 chunks; embedded at 768 dims (nomic) that's ~50 MB of vectors. Storable in SQLite with the `sqlite-vec` extension OR ChromaDB OR just numpy pickled — no need for a heavyweight vector DB.

**Refresh:** hook the RAG index into the existing daily walker chain. Every walker that already writes to PG or disk gets a follow-up step that upserts embeddings for changed rows/files. Cost per full rebuild: ~30 seconds on M4 with nomic-embed batching.

### (b) TOOLS — wire the local model to OUR MCP server

**This is the big one — infrastructure already built.**

The MCP server at `mcp.xrpldashboard.com/mcp` currently serves **15 tools**, all returning proof envelopes with `{source, as_of, freshness_contract, cross_check_status, methodology_url, honest_partial}` (verified end-to-end from a clean outside client 2026-09-12 20:22 EDT post-restart). A local Ollama model becomes a client of this server:

```
┌──────────────┐   loopback   ┌──────────┐   HTTPS   ┌───────────────────────────────┐
│  local LLM   │ ────────────▶│   MCP    │ ─────────▶│ mcp.xrpldashboard.com/mcp     │
│ (Ollama,     │              │  bridge  │           │ (15 tools, proof envelopes)   │
│  Qwen2.5-7B) │◀──────────── │ (python) │◀───────── │                               │
└──────────────┘  tool result └──────────┘           └───────────────────────────────┘
```

The bridge is ~200 lines of Python: Ollama chat API → tool descriptor injection → MCP JSON-RPC call → structured tool result → back into LLM's context as a `tool` message. Reference implementation is standard — every MCP-native chat client (Anthropic Desktop, Cursor, Continue.dev) does exactly this.

**Every answer that requires ledger/registry data is grounded in a tool result whose proof envelope is embeddable in the UI.** "The chain root for 2026-09-12 is `914fbbe8…54e199c4`, per signed_snapshot_walker (source), as_of 2026-09-13T00:23Z, freshness_contract ≤ 5min. Verify at /methodology#snapshot-recipe." The model NEVER answers from raw recall for anything ledger-related.

Fifteen tools currently:
`get_ledger_stats, get_amendment_status, get_unl_status, get_whale_events, get_whale_watchlist, get_rlusd_supply, get_rlusd_flow_24h, get_amm_pool, get_amm_top_by_tvl, get_token_attestation, get_rwa_families, get_rwa_pools, get_mpt_snapshot, get_signed_snapshot, verify_snapshot_signature`

**Gap (post-freeze small work):** three more tools worth adding for the local-LLM use-case — `search_tokens(query)`, `search_issuers(query)`, `get_recent_changes(days)`. Each is a thin wrapper over PG queries the site already runs.

### (c) FINE-TUNE — only if a specific task plateaus below eval floor

**Framework on Apple Silicon:** MLX-LM (Apple's official LLM lib for Metal 4), or Unsloth + PEFT LoRA. Both do LoRA fine-tunes of 4B-8B models on 16 GB unified memory in hours, not days.

**Candidate task:** the token-category classifier. `token_category_history` has curator-labeled examples of `(token_currency, issuer, category, tier, notes, verdict, cited_source)`. If curator has labeled >2,000 rows, we can LoRA-fine-tune Qwen2.5-7B → "token-category-judge-v1" that classifies (currency, issuer, symbol, on-chain-domain, holders, trust-lines-count) → {verified, self-described, labeled, bare, unknown} + confidence + one-sentence rationale.

**Rule (from feedback_llama_8b_insufficient):** do NOT fine-tune before running the RAG + tools evaluation. Small fine-tunes often underperform strong RAG+tool baselines on structured-lookup tasks. Fine-tune only if:
1. The RAG+tools eval on the classification questions (Q7-Q13 below) scores <85%
2. There are >1,000 curator-labeled training examples with balanced class distribution
3. Two curator readers can independently reproduce the label from `notes` alone

**Estimated examples needed:** ~800-1500 for a competent LoRA on Qwen2.5-7B for this narrow task. Verify curator has that count before starting.

## 9. WHAT IT'S FOR — ranked

**(i) "Ask the ledger" assistant on the site — SHIP FIRST.**

Why first: it's the surface that leverages the tool infrastructure we just proved end-to-end this weekend (15/15 MCP tools with proof envelopes) AND it's the paid-tier gating question. If tool-grounded answers work internally, they'll work for external MCP consumers hitting the same rails. Public URL `/ask` or `/assistant` (post-freeze, behind a "beta — answers from our verified data only, everything cited" banner). Failure mode is well-bounded: worst case is "not in my data" (safe), not a wrong claim.

**(ii) Curation triage — SHIP SECOND (internal-only).**

Internal Charlie-only tool. Given a newly-seen token / issuer / message, the LLM proposes a category (verified / self-described / labeled / bare / unknown / warning-class), with citations. Charlie sees the proposal + edits + approves. Nothing goes public without curator sign-off. Safer surface to validate LLM judgment because a human always sees it before publish. Also generates curator-labeled examples that flow into the potential fine-tune corpus.

**(iii) /check message classifier's second opinion — SHIP THIRD (narrow, tool-driven).**

Narrow task: user pastes a message ("send 500 USDC to r… and I'll send you 1000 back"). Current /check has heuristic detectors. The LLM adds a second opinion — "does this match known scam patterns?" — with citations to /methodology + specific detector rules. Reason to ship third: the current /check heuristics are correct enough that we're refining, not replacing. Adds value at the margin.

**(iv) Daily changelog plain-English lines — SHIP FOURTH (bounded drafting).**

Given the day's changes_envelope (which is already machine-generated fact), the LLM drafts a one-sentence plain-English summary. Charlie edits, ships. Small drafting task, easy to validate against source facts. Not moat, but nice.

**Why NOT ship the fine-tune first (deferred until eval measures the gap):**

Fine-tuning a token-category-judge is tempting but premature. RAG+tools on Qwen2.5-7B against the same corpus will likely score 85%+ on questions Q7-Q13 without any fine-tune. Only invest fine-tune cycles if the eval measures a specific plateau on structured-classification questions the RAG+tools baseline can't clear.

## 11. LATER — post-launch considerations

- **7B → 14B tradeoff:** If /ask usage grows and quality on complex questions plateaus, upgrade to Qwen2.5-14B (fits 16 GiB tight but works). Tokens/sec drops ~2× but quality gains are meaningful on multi-step reasoning.
- **Second-node cluster** (already on the strategy list): a second Mac with Ollama + a copy of the RAG index gives us failover for /ask and doubles throughput. Cost: another Mac mini or an M-series MBP.
- **Public MCP-tier stratification (paid tier via x402):** post Fence-#8 close, `/ask` becomes an x402-metered tool endpoint. Same infrastructure; just flip billing on.
- **Model rotation:** every ~3-6 months a new open model materially improves. Set a walker or cron reminder to re-run the eval against the current top-3 open models and pick the winner. The eval is the durable artifact; the model is swappable.
